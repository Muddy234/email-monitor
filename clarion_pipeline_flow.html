01token-check
Validates Outlook token + Supabase session. Bails if either missing or expired.
gate · both tokens required

Validates both the Outlook token via isTokenExpired() and the Supabase session via getSupabaseSession(). Bails immediately with an error object if either is missing or expired. Extracts userId from session.user.id for all downstream steps.

02user-change-detection
If different user than last sync, loads that user's state from chrome.storage.local (sync:{userId}).
writes · resets in-memory state

Compares the current userId against in-memory currentUserId. If they differ (or on first run), calls loadUserStateIntoMemory(userId) which reads the per-user blob at chrome.storage.local["sync:{userId}"] and hydrates lastSyncTime, foldersCache, and connectedOutlookEmail from that blob. Each user has their own keyed state; switching accounts naturally loads that account's values (or nulls on first sync) without needing an explicit wipe.

Fetches the user's profile from Supabase via getProfile(userId) to retrieve connected_outlook_email, onboarding_completed_at, and initial_sync_complete flags. Extracts outlookEmail from the token via getOutlookEmail(token.token). Profile data gates subsequent account-lock and sync-mode logic.

Sets the in-memory flag hasCompletedFolderSync = true if profile.initial_sync_complete === true, restoring folder discovery state that would otherwise be lost when the MV3 service worker terminates. This allows subsequent syncs to skip DOM polling and use the cached folder list.

05outlook-account-lock
First sync locks connected_outlook_email. Subsequent syncs verify token matches the lock.
writes · profiles.connected_outlook_emailgate · mismatch = abort

On first sync (when profile.connected_outlook_email is null), locks the Outlook account by calling setConnectedOutlookEmail(userId, outlookEmail). On subsequent syncs, verifies the token account matches the lock and aborts with {error: "OUTLOOK_MISMATCH"} if it doesn't. Clears stale mismatch state on match or if no outlookEmail is found.

Calls discoverMailFolders() to read the Outlook sidebar DOM via chrome.scripting, returning subfolder IDs. 08per-folder-fetch-push
For each folder: handleGetEmails() → enrichEmailsBatched() → pushEmails() to Supabase.
writes · emails tableper-folder errors non-blocking

Loops through each folder sequentially: handleGetEmails() → enrichEmailsBatched() → maps rows with user_id, email_ref, subject, sender, body (capped at 50 KB), recipients, etc. → pushEmails() to Supabase. Status defaults to "unprocessed" via DB trigger. Per-folder failures are non-blocking; the loop continues to the next folder.

09sent-items-sync
Separate fetch for Sent Items. Status set to completed (not queued for drafts).
writes · emails table (status=completed)

Separate non-blocking fetch via handleGetSentItems() using the same pre/post-onboarding cap as step 07 (500 or 50). Enriches via enrichEmailsBatched(), transforms rows with status: "completed" (intentionally not queued for draft generation), and pushes to Supabase. Sent-items failure doesn't block inbox sync completion.

10persist-lastSyncTime
Saves sync timestamp after all folder fetches complete. Persisted to chrome.storage.local.

Sets lastSyncTime = new Date().toISOString() and calls writeUserState(userId, { lastSyncTime }) to merge into the per-user blob at chrome.storage.local["sync:{userId}"]. Account identity is carried by the key itself, so no separate lastSyncUserId is needed. This timestamp gates incremental vs. catchup mode in future cycles (steps 06 and 07).

Calls detectAndUpdateAliases(userId, authEmail, sentEnriched) using the auth email from session.user.email and sender addresses extracted from sent items. Updates profiles.user_email_aliases in Supabase so downstream classification can correctly identify the user's own messages.

12heartbeat
Updates last_heartbeat_at so the worker knows the extension is active.
writes · profiles.last_heartbeat_at

Calls updateHeartbeat(userId) (errors caught silently via .catch(() => {})) to update profiles.last_heartbeat_at. The Python worker uses this timestamp to determine whether the extension is active — if stale for more than 15 minutes, the worker falls back to business-hours heuristics.

13signal-initial-sync
If hasCompletedFolderSync=true AND initial_sync_complete=false → PATCHes to true.
writes · profiles.initial_sync_completePATCH failure → retries next cycle

If hasCompletedFolderSync === true AND profile.initial_sync_complete === false, calls setInitialSyncComplete(userId) to PATCH the flag to true in Supabase, gating the Phase B onboarding pipeline. Runs after ALL folder syncs complete to prevent the "flag set but emails not landed" race. Per-folder failures in step 09 are non-blocking, so partial folder coverage is possible — the email_count >= 500 gate in Phase B mitigates this.

Hardening note

Step 13 runs after ALL folder syncs complete, preventing the 'flag set but emails not landed' race. But per-folder failures in step 08 are non-blocking — a user could have initial_sync_complete=true with only partial folder coverage. The email_count >= 500 gate in Phase B mitigates this.

15get-users-needing-onboarding
Queries profiles table with all four gate conditions. Returns list of eligible user IDs.
reads · profiles table

Queries the profiles table with four gate conditions: onboarding_completed_at IS NULL, onboarding_status in {null, pending, failed}, initial_sync_complete = true, and email_count >= 500. Returns a list of eligible user IDs that haven't been onboarded yet, filtering out users still syncing or with insufficient email volume for meaningful profiling.

16run-onboarding
Calls into runner.py to execute the three-stage pipeline. Progresses through granular status values at each stage.
writes · onboarding_status = starting → collecting → statistics → persisting → extracting → synthesizing → style_guide → training → complete

Invokes run_onboarding(db, uid, profile) from runner.py, which executes the full three-stage onboarding pipeline. Sets onboarding_status = "starting" on entry, then advances through granular progress states as each stage runs: collecting → statistics → persisting → extracting (Haiku) → synthesizing (Sonnet) → style_guide (final writes) → training (classifier) → complete or complete_partial. Edge case: if the function crashes mid-flight, status remains at whichever intermediate value was last written and blocks all future attempts — the stuck-onboarding recovery in _recover_stuck_onboarding() resets any non-terminal status to "pending" on worker restart.

Hardening note

If step 16 crashes mid-pipeline, onboarding_status stays at whichever intermediate value (starting, collecting, synthesizing, etc.) was last written — the gate condition (status in {null, pending, failed}) blocks all future attempts. _recover_stuck_onboarding() mitigates this on worker restart by resetting any non-terminal status back to "pending", but an in-process watchdog would catch stalls without requiring a restart.

17collect-emails

Calls collect_onboarding_emails() which fetches up to 1500 emails over 180 days, filters spam/noise using blacklist senders (noreply@, mailer-daemon@, etc.) and subject patterns (accepted:, declined:, etc.), removes calendar invites (iCalendar content) and empty bodies (<10 chars), then caps at 500. 18style-gate
If < 30 sent emails, sets skip_guides = True. Onboarding continues without style/behavioral guides.
gate · 30 sent minimum for guides

If fewer than 30 sent emails exist, sets skip_guides = True. Onboarding continues without style or behavioral guides. This cascades downstream: style guide synthesis requires ≥15 features (MIN_STYLE_FEATURES), and behavioral synthesis requires ≥10 features (MIN_BEHAVIORAL_FEATURES). All guide dependencies fail gracefully, enabling partial onboarding (complete_partial status).

Stage 2 — AI enrichment (Haiku + Sonnet)
Haiku extraction — 3 parallel passes

Email features

Received emails. Signal extraction: consequence, action request, bottleneck, deadline, response type.

failure → abort onboarding

Style features

Sent emails. Greetings, sign-offs, formality, sentence structure, verbal habits, punctuation.

failure → skip style guide

Behavioral features

Sent + received pairs. Decision type, commitment pattern, scope behavior. + decision quotes for preference extraction.

failure → skip behavioral + preference

Hardening note — Haiku fan-in

Behavioral extraction failure now kills both the behavioral profile AND the preference profile, because decision quotes are extracted alongside behavioral features. If behavioral Haiku returns a malformed response, decision_moments defaults to [] and preference synthesis receives nothing.

25train-classifier
Trains per-user importance model from email features.

Calls train_user_model(db, user_id) which fetches response_events (requires ≥30 events, uses defaults if insufficient), computes global_rate (fraction of emails responded to), derives lift factors from boolean features (user_position, subject_type, msg_type, recipient_count_bins, thread_depth_bins), detects recurring patterns (cadence, same-sender sequences), fits isotonic regression, and computes triage thresholds (hard_gate at 0.01, soft_gate at 0.03). Stage 1 — Rule-based filtering
28filter-emails
Marks pre-onboarding arrivals as 'onboarding', then runs rule-based filter + signal-based auto-skip. Skipped emails written to DB immediately.
writes · emails.status = onboarding/processed, classifications (skip)reads · emails, profiles.onboarding_completed_atempty result → early exit

Three-phase filter executed by filter_emails(). Phase 0 — Late-arrival sweep: If profile.onboarding_completed_at is set, any email with received_time < onboarding_completed_at is a historical catchup arrival and gets bulk-updated to status = "onboarding" via db.bulk_update_email_status(), then dropped from the batch. Phase 1 — Rule-based: EmailFilter.classify() checks blacklist senders (noreply@, mailer-daemon@), blacklist subject patterns (accepted:, out of office), whitelists, and project keywords. Empty-body emails are deferred (kept as "unprocessed") for up to 10 minutes to allow re-sync. Phase 2 — Signal auto-skip: _should_auto_skip() catches terminal acknowledgments ("Thanks", "Got it") and FYI-language emails. Skipped emails are batch-written to DB immediately (status = processed, classification = skip reason).

Early exit — all filtered out

  • All emails were late arrivals, blacklisted, or auto-skipped — nothing reaches Stage 2

Fetches contacts, threads, domain tiers, feedback summaries. Upserts contact stats for unknown senders. Labels retroactive responses.

Fetches five data sources for signal extraction: (1) _fetch_batch_context() — per-sender contacts and per-conversation threads. (2) _fetch_thread_emails_batch() — prior emails in each thread for content isolation. (3) _get_domain_tiers() — domain-level tier overrides. 30pre-process-bodies
Per email: isolates new content from thread history, strips signatures, truncates to 2500 tokens via pre_process_email().
reads · email body + thread_emails_map

Per-email body preparation for Haiku. Calls pre_process_email() which runs three transformations: (1) isolate_new_content() — diffs against prior thread bodies to strip quoted/replied text, leaving only the newest message (forwards left intact). (2) strip_signatures() — removes "Best regards", "Kind regards", confidentiality disclaimers from the tail. (3) truncate_smart() — caps at ~2500 tokens; if over limit, takes first 1600 chars + [... truncated ...] + last 1600 chars. Also resolves per-email metadata: sender tier via resolve_sender_tier() (waterfall: contact override → domain_tiers → org domain → prior history → unknown), thread depth and unanswered status via compute_thread_meta(), user position (TO vs CC), and feedback hints.

Stage 3 — Signal extraction (Haiku batch)
31signal-extraction-batch
Submits Haiku batch via Anthropic Batches API. Extracts 9 signals per email: mc, ar, ub, dl, rt, target, pri, draft, reason.
writes · token_usage (haiku/signals)reads · pre-processed bodies + contextbatch failure → sync fallback

Constructs one extract_signals_batch_params() request per email and submits to the Anthropic Batches API (Haiku, temp=0, max_tokens=200). Each request includes: pre-processed body, subject, sender metadata (name, email, tier, contact_type, significance), thread metadata (depth, has_unanswered), user identity (name, email, position, TO/CC fields), and feedback hints. Returns 9 signals per email: mc (material consequence), ar (action request), ub (user bottleneck), dl (deadline), rt (response type: none/ack/ans/act/dec), target (user/other/all/unclear), pri (high/med/low), draft (boolean), reason (truncated to 200 chars post-parse). Polls at BATCH_POLL_INTERVAL (default 3s) for up to BATCH_MAX_WAIT (default 900s).

For emails missing batch results: runs synchronous extract_signals() one-by-one. Same signals, higher latency.

Iterates emails missing from batch_results (batch failed or individual results returned null). For each, calls synchronous extract_signals() — a single Anthropic API call producing the same 9 signals. Results are JSON-serialized back into batch_results for uniform downstream post-processing. Stage 4 — Post-process + classify
33post-process-signals
Parses signal JSON, applies contact overrides (VIP, priority, draft preference), builds response_events, writes classification. Appends to unified candidates list with route=draft|notable.
writes · classifications, emails.status = processed, response_eventsreads · batch_results, contacts_map

Iterates every email in email_context. For each: (1) Parses signal JSON via parse_signal_response() with field coercion and fallback defaults. (2) Applies _apply_contact_overrides(): is_vip → pri=high, priority_override → overrides pri, draft_preference=always → forces draft=True, =never → forces draft=False. Hard override: ar=True + target=other → draft=False. (3) Builds response_event and writes classification. (4) Appends to a single candidates list with a route field: draft=True + age < 24h + generation enabled → route="draft" (with style_guide, behavioral_profile, preference_profile in action_context). Otherwise if notable criteria match (pri=high/med, mc=True, tier=C/I, rt != none) → route="notable". Downstream stages filter by route ([c for c in candidates if c["route"]=="draft"]).

Email routing — two paths

Draft path

draft=True + age < 24h + generation enabled. Collects style_guide, behavioral_profile, preference_profile into action_context.

Notable path

draft=False but pri=high/med, mc=True, tier=C/I, or rt != none. Queued for summary generation.

Stage 5 — Draft generation (Sonnet batch)
35draft-generation-batch
Sonnet batch with 3-layer profile injection (style + behavioral + preference). Deduplicates candidates. Builds batch via DraftGenerator.build_batch_params().
writes · token_usage (sonnet/draft)reads · candidates (route=draft), style_guide, behavioral_profile, preference_profilebatch failure → per-draft sync fallback

Initializes DraftGenerator with config. DEFAULT_DRAFT_PROMPT_TEMPLATE is None — there is no system prompt; instructions are assembled into a single structured user message. Deduplicates candidates by db_id. build_batch_params() composes the user message with labeled sections: PERSONALITY PROFILE (style guide — how to write), BEHAVIORAL PROFILE (how to express decisions), PREFERENCE PROFILE (what to decide — Investment Orientation + Positional Stance), followed by NEVER rules, the EMAIL body, optional THREAD SUMMARY/CONTACT SUMMARY, and a final "Draft a reply" instruction. Null profile layers are omitted (graceful degradation). Submits as Sonnet batch (temp=0.3, max_tokens=2048). Fallback to sync generate_draft() for missing batch results. The model's output may include <thinking>…</thinking> blocks which are stripped by post-processing and retained separately as response_events.summary. Output validated via _validate_output() (rejects NO_DRAFT_NEEDED, <20 chars, error messages).

Three-layer draft composition

Each draft uses three profile layers composed into a single user message (no system prompt): style guide (how to write), behavioral profile (how to express decisions), and preference profile (what to decide). The preference layer resolves decision direction via Investment Orientation and Positional Stance. Null layers are omitted — graceful degradation, not failure.

36quality-check
5-check QC pipeline: leaked artifacts, tag hygiene, sign-off, greeting, word count. Auto-fixes minor issues. Single retry with revision notes on failure.
writes · token_usage (sonnet/draft) on retryreads · draft body, style_guide (QC config)retry failure → deliver with quality_issues

Five-check QC pipeline via check_draft_quality(): (1) Leaked artifacts — strips <thinking> fragments, "Here's a draft" meta-commentary, header leaks. (2) Tag hygiene — removes standalone [USER TO CONFIRM] before content, deduplicates tags, flags unclosed brackets and bare [PLACEHOLDER]. (3) Sign-off — validates closing greeting + correct user name; auto-fixes double sign-offs; flags truncated/wrong names for retry. (4) Greeting — validates opening salutation addresses recipient, not user. (5) Word count — flags drafts outside 0.25x–3x target range (from style guide). QCConfig is parsed once per user from the style guide via parse_qc_config().

QC retry semantics

If the first QC check fails, a single retry is attempted with build_revision_notes() injected into the prompt. If the retry also fails QC, the draft is delivered with quality_issues recorded. If retry returns nothing, the original draft is kept with issues flagged. No second retry — prevents API cost spiraling.

37persist-drafts
Inserts passing drafts via db.insert_draft(). Records quality_issues and quality_retry_count. Stores draft thinking as response_events.summary.

For each candidate with a non-null cleaned draft: calls db.insert_draft(db_id, user_id, cleaned) with optional quality_issues and quality_retry_count.
