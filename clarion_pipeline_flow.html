Validates both the Outlook token via isTokenExpired() and the Supabase session via getSupabaseSession(). Bails immediately with an error object if either is missing or expired. Extracts userId from session.user.id for all downstream steps.

02user-change-detection
If different user than last sync, wipes lastSyncTime, cachedFolders, connectedOutlookEmail.

Compares the current userId against lastSyncUserId stored in chrome.storage.local. If they differ (or on first run), resets lastSyncTime, connectedOutlookEmail, cachedFolders, and folderCacheTime to force a full catchup on account switch. Stores the new lastSyncUserId to prevent repeated resets.

Fetches the user's profile from Supabase via getProfile(userId) to retrieve connected_outlook_email, onboarding_completed_at, and initial_sync_complete flags. Extracts outlookEmail from the token via getOutlookEmail(token.token). Profile data gates subsequent account-lock and sync-mode logic.

04seed-folder-sync

Sets the in-memory flag hasCompletedFolderSync = true if profile.initial_sync_complete === true, restoring folder discovery state that would otherwise be lost when the MV3 service worker terminates. This allows subsequent syncs to skip DOM polling and use the cached folder list.

05outlook-account-lock
First sync locks connected_outlook_email. Subsequent syncs verify token matches the lock.
writes · profiles.connected_outlook_emailgate · mismatch = abort

On first sync (when profile.connected_outlook_email is null), locks the Outlook account by calling setConnectedOutlookEmail(userId, outlookEmail). On subsequent syncs, verifies the token account matches the lock and aborts with {error: "OUTLOOK_MISMATCH"} if it doesn't. Clears stale mismatch state on match or if no outlookEmail is found.

Calls discoverMailFolders() to read the Outlook sidebar DOM via chrome.scripting, returning subfolder IDs. 07set-email-cap

gate · onboarding_completed_at

Determines the maxEmails per-folder cap: 200 if isInitialSync (onboarding incomplete AND folders not yet discovered), 50 if lastSyncTime exists (incremental mode), or MAX_CATCHUP_EMAILS for a full catchup. Logs the sync mode state for debugging.

08per-folder-fetch-push
For each folder: handleGetEmails() → enrichEmailsBatched() → pushEmails() to Supabase.
writes · emails tableper-folder errors non-blocking

Loops through each folder sequentially: handleGetEmails() → enrichEmailsBatched() → maps rows with user_id, email_ref, subject, sender, body (capped at 50 KB), recipients, etc. → pushEmails() to Supabase. Status defaults to "unprocessed" via DB trigger. Per-folder failures are non-blocking; the loop continues to the next folder.

09sent-items-sync
Separate fetch for Sent Items. Status set to completed (not queued for drafts).

Separate non-blocking fetch via handleGetSentItems() with the same maxSentEmails cap logic (50 if incremental, else MAX_CATCHUP_EMAILS). Enriches via enrichEmailsBatched(), transforms rows with status: "completed" (intentionally not queued for draft generation), and pushes to Supabase. Sent item failure doesn't block inbox sync completion.

Sets lastSyncTime = new Date().toISOString() and calls persistSyncTime() to write to chrome.storage.local after all folder and sent fetches complete. Also stores lastSyncUserId to track account identity. This timestamp gates incremental vs. catchup mode in future cycles (steps 06 and 07).

Calls detectAndUpdateAliases(userId, authEmail, sentEnriched) using the auth email from session.user.email and sender addresses extracted from sent items. Updates profiles.user_email_aliases in Supabase so downstream classification can correctly identify the user's own messages.

12heartbeat
Updates last_heartbeat_at so the worker knows the extension is active.
writes · profiles.last_heartbeat_at

Calls updateHeartbeat(userId) (errors caught silently via .catch(() => {})) to update profiles.last_heartbeat_at. The Python worker uses this timestamp to determine whether the extension is active — if stale for more than 15 minutes, the worker falls back to business-hours heuristics.

13signal-initial-sync
If hasCompletedFolderSync=true AND initial_sync_complete=false → PATCHes to true.
writes · profiles.initial_sync_completePATCH failure → retries next cycle

If hasCompletedFolderSync === true AND profile.initial_sync_complete === false, calls setInitialSyncComplete(userId) to PATCH the flag to true in Supabase, gating the Phase B onboarding pipeline. Runs after ALL folder syncs complete to prevent the "flag set but emails not landed" race. Per-folder failures in step 09 are non-blocking, so partial folder coverage is possible — the email_count >= 500 gate in Phase B mitigates this.

Hardening note

Step 14 runs after ALL folder syncs complete, preventing the 'flag set but emails not landed' race. But per-folder failures in step 09 are non-blocking — a user could have initial_sync_complete=true with only partial folder coverage. The email_count >= 500 gate in Phase B mitigates this.

Queries the profiles table with four gate conditions: onboarding_completed_at IS NULL, onboarding_status in {null, pending, failed}, initial_sync_complete = true, and email_count >= 500. Calls collect_onboarding_emails() which fetches up to 1500 emails over 180 days, filters spam/noise using blacklist senders (noreply@, mailer-daemon@, etc.) and subject patterns (accepted:, declined:, etc.), removes calendar invites (iCalendar content) and empty bodies (<10 chars), then caps at 500. 18style-gate
If < 30 sent emails, sets skip_guides = True. Onboarding continues without style/behavioral guides.
gate · 30 sent minimum for guides

If fewer than 30 sent emails exist, sets skip_guides = True. Onboarding continues without style or behavioral guides. This cascades downstream: style guide synthesis requires ≥15 features (MIN_STYLE_FEATURES), and behavioral synthesis requires ≥10 features (MIN_BEHAVIORAL_FEATURES). All guide dependencies fail gracefully, enabling partial onboarding (complete_partial status).

Stage 2 — AI enrichment (Haiku + Sonnet)
Haiku extraction — 3 parallel passes

Email features

Received emails. Signal extraction: consequence, action request, bottleneck, deadline, response type.

failure → abort onboarding

Style features

Sent emails. Greetings, sign-offs, formality, sentence structure, verbal habits, punctuation.

failure → skip style guide

Behavioral features

Sent + received pairs. Decision type, commitment pattern, scope behavior. + decision quotes for preference extraction.

failure → skip behavioral + preference

Hardening note — Haiku fan-in

Behavioral extraction failure now kills both the behavioral profile AND the preference profile, because decision quotes are extracted alongside behavioral features. If behavioral Haiku returns a malformed response, decision_moments defaults to [] and preference synthesis receives nothing.

25train-classifier
Trains per-user importance model from email features.
failure → non-fatal

Calls train_user_model(db, user_id) which fetches response_events (requires ≥30 events, uses defaults if insufficient), computes global_rate (fraction of emails responded to), derives lift factors from boolean features (user_position, subject_type, msg_type, recipient_count_bins, thread_depth_bins), detects recurring patterns (cadence, same-sender sequences), fits isotonic regression, and computes triage thresholds (hard_gate at 0.01, soft_gate at 0.03). Bulk updates all emails that were part of the onboarding sample to status "onboarding". This prevents them from being picked up by accumulate_emails() in Phase D. Only emails arriving after this step will be processed for drafts.

27mark-complete

Sets onboarding_status to "complete" (or "complete_partial" if style_guide or behavioral_profile is missing) and writes onboarding_completed_at timestamp. complete_partial is set when style or behavioral guides are missing (skip_guides was true, or synthesis failed). A missing preference profile does NOT trigger complete_partial — the preference layer is additive. Setting onboarding_completed_at is the gate that unlocks Phase D normal processing.

28accumulate-emails
Processes users where onboarding_completed_at is not null. New emails get signal extraction + draft generation.
writes · drafts tablereads · emails (status=unprocessed)

Only runs for onboarded users. Picks up emails that arrived after step 26 (status="unprocessed"). For each email: runs signal extraction (5 Haiku signals via Anthropic Batches API), applies the chain-of-thought draft generation with the three-layer profile (style + behavioral + preference), and writes the draft. The preference profile is loaded alongside the other two guides and injected into the draft prompt. If preference_profile is null, the preference section is simply omitted. QC check validates greeting/sign-off presence and word count; retries once with revision notes on failure.

Three-layer draft composition

Each draft now uses three profile layers: the style guide (how to write), the behavioral profile (how to express decisions), and the preference profile (what to decide). The preference layer resolves the direction of decisions using Investment Orientation and Positional Stance categories. All three layers are loaded from the profiles table on each draft generation call. Null layers are omitted from the prompt — graceful degradation, not failure.
