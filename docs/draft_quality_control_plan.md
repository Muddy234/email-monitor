# Draft Quality Control Implementation Plan

## Overview

Add a rule-based QC function that runs after `_validate_output` and before `insert_draft`. On failure, retry once with targeted feedback. If retry also fails, deliver draft with `quality_issues` flag.

## Files to create/modify

| File | Action |
|------|--------|
| `worker/pipeline/quality_check.py` | **Create** — all QC logic + style guide parsing |

## Step 1: Migration — `032_draft_quality_issues.sql`

```sql
ALTER TABLE public.drafts
  ADD COLUMN IF NOT EXISTS quality_issues jsonb DEFAULT NULL,
  ADD COLUMN IF NOT EXISTS quality_retry_count integer DEFAULT 0;
```

- `quality_issues`: NULL = passed QC. Populated = JSON array of **un-fixed** issue strings only. Auto-fixed issues are logged but not persisted here — the user should never see issues that were already resolved.
- `quality_retry_count`: 0 = no retry needed. 1 = retried once. Enables tracking retry rates and per-issue-type retry success rates.

    """Rule-based quality check on a generated draft."""

### Style guide parsing approach

The style guide is free-form text generated by Sonnet during onboarding. Parsing is best-effort with safe defaults — if we can't extract a value, we assume the conservative default (greetings expected, sign-off expected, no length check). Specific patterns to look for:
- Greeting: look for "pleasantries" or "greeting" mentions. If guide contains "minimal pleasantries" or shows a greeting pattern like `[First Name],` with no Hi/Hello prefix, set `greetings_expected = False`.
- Sign-off: look for "sign-off" mentions. Only set `signoff_expected = False` if guide explicitly says no sign-off. This is rare.
- Word range: look for word count targets (e.g., "40-80 words", "typically under 100 words"). Extract as tuple. If not found, `target_word_range = None` and length check is skipped.

### Checks (in execution order)

**A. Leaked artifacts (auto-fix, no retry)**
- `<thinking>` fragments — strip residual `</?thinking>` tags
- Meta-commentary prefix — strip known AI preamble lines from start of draft. Uses an exact allowlist of prefix patterns followed by a line break:
  - `"Here's a draft"`, `"Here is a draft"`, `"Here's my response"`, `"Here is my response"`
  - `"Sure, here's"`, `"Sure, here is"`
  - `"I'll draft"`, `"Let me draft"`
  - Match only when the pattern is on its own line (followed by `\n`), not inline with email content. `"Here's the breakdown of Q1 numbers"` is real content and must not match.
- Header/subject leak — strip `Subject:`, `Re:`, `To:`, `From:`, `CC:` lines from start of draft only (first 3 lines)

**B. Tag hygiene (mixed)**
- Standalone `[USER TO CONFIRM]` before greeting — auto-fix: strip the block. A standalone block is a line containing only the tag (with optional whitespace), appearing before the first greeting or body line.
- Duplicate `[USER TO CONFIRM]` with same description (case-insensitive) — auto-fix: keep first occurrence, remove duplicates
- Unclosed brackets `[` without matching `]` — flag only (no retry, no auto-fix)
- Bare `[PLACEHOLDER]` without specific description — flag only

**C. Sign-off (conditional on `signoff_expected`)**
- **Skip all sign-off checks if `signoff_expected = False`**
- Missing sign-off — no sign-off greeting pattern (Best regards, Thanks, Regards, etc.) in last 5 lines → triggers retry
- Truncated user name — sign-off greeting exists but the name on the following line doesn't match `user_name`. Partial prefix match (e.g., "Nat" for "Nate McBride") confirms truncation → triggers retry
- Double sign-off — two or more sign-off greeting matches in the draft → auto-fix: keep last sign-off block only

**D. Greeting (conditional on `greetings_expected`)**
- **Skip missing-greeting check if `greetings_expected = False`**
- Missing greeting — first non-empty line has no Hi/Hello/Hey/Dear/Good morning/etc. → triggers retry (only when `greetings_expected = True`)
- Greeting addresses user — greeting line contains `user_name` (or user's first name) and `recipient_name` is different. **Skip this check entirely if `multi_recipient = True`** (greeting could be "Hi all," or any individual's name). When `recipient_name` is empty, only the negative check runs (greeting contains user's own name) — the positive check (correct name used) cannot run. This is documented and acceptable.

**E. Length sanity (flag only, never retries)**
- **Skip if `target_word_range` is None** (couldn't parse from style guide)
- Count words in draft. Flag if outside 0.25x–3x of the target range.
- This catches pathological outputs (3-word reply to multi-part question, or 500-word essay from a terse user) but doesn't trigger retry — the model chose that length intentionally. Flagged in `quality_issues` for production monitoring.

### Decision matrix

| Issue | Auto-fix? | Triggers retry? | Conditional? |
|-------|-----------|-----------------|--------------|
| `<thinking>` fragments | Yes | No | — |
| Meta-commentary prefix | Yes | No | — |
| Header/subject leak | Yes | No | — |
| Standalone `[USER TO CONFIRM]` | Yes | No | — |
| Duplicate `[USER TO CONFIRM]` | Yes | No | — |
| Double sign-off | Yes | No | `signoff_expected` |
| Unclosed brackets | No | No (flag only) | — |
| Bare `[PLACEHOLDER]` | No | No (flag only) | — |
| Missing sign-off | No | **Yes** | `signoff_expected` |
| Truncated user name | No | **Yes** | `signoff_expected` |
| Missing greeting | No | **Yes** | `greetings_expected` |
| Greeting addresses user | No | **Yes** | Not `multi_recipient` |
| Length outside range | No | No (flag only) | `target_word_range` set |

### `quality_issues` storage rule

Only **un-fixed** issues are stored in the `quality_issues` DB column. Auto-fixed issues are included in `QCResult.auto_fixed` for logging but are **not persisted** — the user should never see issues that were already resolved in the delivered draft.

## Step 3: Targeted retry via `revision_notes`

### Change to `drafts.py`

Add optional `revision_notes` parameter to `generate_draft()` and `_build_draft_prompt()`. When provided, append to the user prompt:

```
REVISION NOTE: The previous draft had these structural issues: {issues}.
Please ensure the reply corrects these problems.
```

This gives the model targeted feedback on what went wrong, rather than a blind re-roll with the same prompt. Without this, retry success rate will be low — the model made the structural error for a reason.

The `revision_notes` string is built by the caller from `QCResult.issues`. Example:
- `"Missing sign-off. The reply must end with a closing greeting (e.g., Best regards,) followed by the user's name."`
- `"Greeting addresses the user (Nate) instead of the recipient (Terri). The greeting should address the email's sender."`

### Change to `build_batch_params()`

No change needed — retries always go through the sync `generate_draft()` path, not the batch path.

## Step 4: Integration in `run_pipeline.py`

Replace lines 1233-1266 with a retry-aware loop:

```
# Before the loop: parse QC config once per user
qc_config_base = parse_qc_config(
    user_name=config.get("draft_user_name", ""),
    recipient_name="",  # set per-candidate below
    style_guide=action_context.get("style_guide", ""),
)

for each candidate:
    1. Get draft_body from batch results (or fallback sync)
    2. Validate via _validate_output
    3. If cleaned:
         a. Build per-candidate QC config (set recipient_name, multi_recipient)
         b. Run check_draft_quality(cleaned, qc_config)
         c. Apply auto-fixes (qc.draft)
         d. Log auto-fixed issues if any
         e. If qc.passed → insert_draft(quality_retry_count=0)
         f. If not qc.passed:
              - Build revision_notes from qc.issues
              - Retry generate_draft(revision_notes=revision_notes)
              - Validate retry output
              - Run QC on retry
              - If retry passes → insert_draft(quality_retry_count=1)
              - If retry fails → insert_draft with quality_issues + quality_retry_count=1
              - If retry returns nothing → insert original with quality_issues + quality_retry_count=1
    4. Store thinking as summary (existing logic)
```

### Recipient info

`recipient_name` comes from `candidate["email_data"].get("sender_name", "")` (the person who sent the inbound email = the recipient of the reply).

`multi_recipient`: derive from the email's To/CC fields if available, or default to `False`. Check if `email_data` has a `to_recipients` or `cc_recipients` field with multiple entries.

## Scope notes

- **Edge function path** (`supabase/functions/generate-draft/index.ts`) is not covered by this QC layer. That path is for on-demand regeneration from the dashboard where the user is actively reviewing output. Future scope if needed.
- **Style guide parsing is best-effort.** If the style guide format changes, parsing fails gracefully to safe defaults (greetings expected, sign-off expected, no length check). This is intentional — false negatives (missing a QC issue) are better than false positives (triggering unnecessary retries).
- **Migration number 032** is currently unused. If the preference extraction plan lands first and claims 032, renumber this to 033.
